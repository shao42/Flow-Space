# Flow Space 信箱 — 需求决策记录

> 基于澄清计划中苏格拉底式追问的**拍板结论**。  
> 已确认的用户选择：社交、一对一、专属链接/信箱码配对。  
> 未在对话中逐条回答的项，按 Flow Space「沉浸式写作 + 轻社交」定位给出**推荐默认**（标注 *默认*），后续可改 spec 修订。

---

## 第一层：为什么要在写作应用里放信箱？

### Q1. 用户此刻的痛苦是什么？

| 痛点 | 优先级 | 说明 |
|------|--------|------|
| 写完想给**特定一个人**看 | **主** | 与「一对一 + 分享链接」一致；导出/微信是离散的，无法在应用内延续对话。 |
| 写作过程中需要轻量陪伴/回应 | 次 | 非实时陪写；对方异步回信即可，不引入在线状态。 |
| 离开 App 后仍有人能留言 | 次 | 依赖云端收件与链接回访，见第三层 Q12。 |

*默认结论：* MVP 优先解决 **「写完 → 寄给一个人 → 对方在同一气质界面里回信」**。

### Q2. 若去掉信箱，现有能力缺什么？

- **Export**：生成文件，无会话、无「对方已读」、无在应用内回复。
- **复制文字到微信**：打断心流；丢失雨/雪氛围与统一排版；无法把「这一稿」与后续回信绑在同一房间。
- **分享站点链接**：对方看到的是空编辑器，不是「给你的信」。

*默认结论：* 信箱补足 **应用内、一对一、可往返** 的文本通道，而非替代 Export。

### Q3. 信箱是写作流程的一部分，还是写作之外的频道？

*默认结论：*

- **独立可收起频道**（类比 [`VibeMixer`](../../src/components/VibeMixer.tsx)）：默认不挡编辑器。
- 入口在 chrome 区新增动作（见 spec），**无全局强提醒**（无角标、无自动弹窗）。
- 可选：从当前草稿 **「寄出副本」** 到已选房间，不自动清空编辑器（与 RELEASE 区分）。

### Q4. 与 RELEASE 的关系是什么？

| 动作 | 语义 |
|------|------|
| **RELEASE** | 确认后**清空本地草稿**（现有行为不变）。 |
| **寄信 / SEND** | 将文本**副本**投递到信箱房间；编辑器内容保留，除非用户随后主动 RELEASE。 |

*默认结论：* **完全独立入口** + 可选「从草稿寄出」；**不**把 RELEASE 改成「寄出即销毁」。

## 第三层：链接配对（Q9–Q12）

### Q9. 一个链接代表什么？

*默认结论：* **一个二人信箱房间（Room）**。

- URL 形态（概念）：`https://<host>/<base>/mailbox#<roomId>/<roomSecret>`  
  - `roomId`：服务端索引。  
  - `roomSecret`：放在 **URL fragment**（不发给服务器日志），用于鉴权与（可选）客户端加密密钥派生。
- **不是**「我的公开收信地址」（避免一对多偏离已选的一对一）。
- 创建者生成链接 → 复制发给对方 → 对方打开即加入**同一房间**（最多 2 个活跃参与者，见 spec）。

### Q10. 链接泄露会怎样？

| 风险 | MVP 策略 |
|------|----------|
| 陌生人拿到完整链接 | 可读历史、可发信（与 Snapchat/私密文档链接类似） |
| 缓解 | (1) 高熵 `roomSecret`；(2) UI 明示「链接即钥匙」；(3) **轮换链接** 使旧 secret 失效；(4) Phase 2 可选房间口令 |

*默认结论：* MVP **不**做首次配对握手；靠 secret 长度 + 用户教育。房间口令列入 Phase 2。

### Q11. 如何「换人」？

*默认结论：*

- 用户可 **创建多个房间**（本地列表存 `roomId` + 显示名/对方昵称）。
- **轮换链接**：服务端作废旧 secret，生成新 secret；旧链接立即失效。
- 无「踢人」：一对一下轮换链接即等价于换锁。

### Q12. 跨设备：消息存在哪里？

*默认结论：* **云端持久化**（必选）。

- 电脑生成链接、手机打开同一链接 → 看到**同一会话历史**。
- 仅 localStorage / IndexedDB **不满足**已选的一对一社交目标。
- 客户端可在 localStorage 缓存最近消息以弱网阅读，**以服务端为准**。

## 持久化（决策树 A）

| 选项 | 是否采用 | 理由 |
|------|----------|------|
| 换设备仍可见 | **是** | Q12、用户曾选社交一对一 |
| 仅本机 | 否 | 对方设备无法同步 |
| 阅后即焚 | 否（MVP） | 与「往来」语义冲突；可作 Phase 3 单条消息选项 |

**拍板：云端房间 + 消息表；链接带 roomSecret；TTL 默认 90 天无活动可归档（见 spec）。**

---

## 身份（决策树 B）

| 选项 | 是否采用 | 理由 |
|------|----------|------|
| 注册登录 | MVP 否 | 降低摩擦；与当前无账号产品一致 |
| 链接 + 自选昵称 | **是** | 收件人可知「谁发的」；每设备存 `displayName` |
| 链接即身份 | 否 | 一对一需要区分 A/B 两侧 |
| 完全匿名 | 否 | 弱化一对一意义 |

**拍板：**

- 首次进入房间时提示设置 **昵称**（≤ 32 字），存 `localStorage` 键 `flowspace:mailbox:v1:profile:<roomId>`。
- 服务端消息带 `senderSlot: 'a' | 'b'`（先加入为 `a`，后加入为 `b`）+ `displayName` 快照。
- Phase 2 可选魔法链接账号，用于跨设备统一昵称与房间列表云同步。
